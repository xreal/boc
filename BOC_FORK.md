# Boc fork integration map

This is the operational map of Boc's deliberate differences from `upstream/v2`. It is not a changelog or roadmap. Read it before changing a fork integration or merging upstream.

## Maintenance contract

- Update this file in the same commit that adds, changes, replaces, or removes a fork capability, upstream seam, or upstream API dependency.
- Describe only implemented behavior. Plans and experiments become entries when their code lands.
- Keep product code in fork-owned paths. If an upstream-owned file must change, keep the change narrow and record it here and in `packages/boc/fork-surface.json`.
- Prefer a supported upstream extension point over a Boc workaround. Remove obsolete seams when upstream makes them unnecessary.
- Treat `packages/boc/fork-surface.json` as the exact machine-readable path list and this file as the explanation of intent and coupling.
- The surface audit compares the working tree against the common upstream baseline, includes untracked non-ignored files, and rejects duplicate, stale and unlisted approvals. It checks both sides of renames against the ownership rules.

Development-environment controls use grouped menus and content-sized labeled split buttons. The details panel has a stable viewport-bounded layout, compact container/application summaries, a checkout-owned container table with lifecycle state, independent Docker health, published ports, and individual start/stop/restart actions. Individual actions use freshly verified Docker IDs and share the existing environment operation lock; retries retain the selected container. The panel refreshes idle status every five seconds, keeps prior rows mounted during inspection, and reserves a persistent operation-result footer. Session tab menus keep Rename and Close tab first, followed by an environment submenu and direct checkout shortcuts. Checkout-path copying is available in both menus; macOS desktop additionally opens that checkout in Terminal through the existing platform API.

Operation output uses a lazy read-only `ghostty-web` terminal and the upstream terminal writer. Inspections expose live in-memory output with absolute UTF-8 byte offsets into the bounded 64 KB tail. Replay precedes live callbacks, overlapping bytes are skipped, and decoding spans process chunks. The renderer appends only unseen bytes, preserves paused scrollback, and coordinates live terminal dimensions through a checkout/run-scoped resize RPC. Devenv commands request plain Compose progress; other terminal controls are interpreted rather than stripped. Container logs are a separate timestamp-ordered, searchable, wrapping text viewer: the latest 500 lines bounded to 64 KB refresh every two seconds while following. Both viewers support copy and text download. Terminal scrollback is bounded to 2,000 rows; an expired output window resets the viewer and explicitly reports truncation rather than pretending missing terminal history can be reconstructed.

Boc settings reuse the upstream settings sections, lists and rows for project selection and development-environment controls. The selected project is remembered per server in window preferences; the current project provides the fallback when no saved selection is available. The domain input sits alongside its label, and shared-service details use an expandable note below the controls.

Configured stacks expose Open in browser directly in the session tab menu, before the environment submenu. Its icon reports container state: success for running, danger for stopped or absent containers, and warning for partial, unknown or refreshing/failed inspection. The same status is available as a tooltip and accessible description; container status does not imply HTTP readiness.

Project Controls supplies producer metadata in its native state response: exact agent/MCP configuration files, skill/instruction paths, and registering plugin identity. Origins distinguish System, Global, Project, and Plugin (registered capabilities without a filesystem scope). MCP tools inherit their server's source when available. The Project setup screen uses compact rows, visible origin labels, inline activation/reset/edit controls, explicit Project/Global tabs, and a single existing-project selector that resolves the server and always opens the project's main-checkout context. The scope-specific Config file action shows the exact native configuration path, opens the full JSONC by default, and retains common structured settings without another scope selector. Each capability section owns its Add action, opens a centered category-fixed dialog in the active scope, and remains available when that category is empty. Agent and MCP creation use one form whose ID remains visible through save rather than a separate definition-creation step. The Global tab hides the project selector, states its all-project scope, lists only globally sourced supported capabilities, and omits tools. A global hard-off appears in Project scope as a disabled switch with a direct explanation. System tools and internal compaction/title/summary agents live in prominent count-bearing disclosure cards. Ctrl+F/Cmd+F focuses and selects the shared V2 TextInput, yielding to dialogs. The route is `/boc/controls`; old `/boc/bergflow` links and the local selection preference key remain compatible.

The configuration side panel edits native global or checkout JSONC through authenticated Controls RPC, with structured agent/MCP forms, default-agent selection, skill sources, plugin package registration/removal, and an advanced JSONC editor. Existing-item editors keep type, identity and scope fixed; their JSONC view edits only the selected definition. Add flows prevent duplicate available definitions and use scope-exact `AGENTS.md` existence metadata to offer editing instead of creation. Form edits use `jsonc-parser` to preserve unrelated content and comments; unsaved drafts require an explicit discard before closing. Inherited copies use raw configuration declarations so environment/file substitutions are retained instead of persisting resolved values. Configuration remains ordinary OpenCode input, including when read by an official server. MCP sign-in/reconnection uses the existing client MCP and integration OAuth APIs through the fork-owned app host bridge; enabled state and connection status are presented separately.

The native `boc.project-controls` built-in activates only in the Boc channel, after configuration producers. Its RPC identity is `boc.controls.v1`, with capability protocol 2 required for global activation scope. Project and global policy plus mutation serialization are process-global services; inventory and scoped subscriptions belong to each Location. Desktop is the supported management UI; there is no CLI/TUI control screen. Native configuration and source-file management are available through the desktop editor. OpenCode's built-in tools are grouped into a collapsed System tools section while custom tools remain visible and searchable.

The host plugin loader uses upstream registration precedence and source handling. The obsolete fork-added fallback registration option and public module-schema export are retired; external embedders using those additions must migrate to ordinary registration. Project Controls does not use either addition. Controls use authenticated plugin RPC through the existing app server client, without changing HTTP APIs or desktop service ownership. Ambient instruction selection is now an internal Location-scoped Controls service; the fork-added external Effect/Promise selection facade is retired. Controls receives structured candidates before filtering, including disabled sources, and permits only project-owned mutations. Nested read-triggered instructions and already admitted Session history are unaffected.

Session search uses the upstream implementation from `370b9965d3` without Boc overrides. The former Boc page-search implementation has been removed.

Environment Start all and Stop all target every freshly ownership-verified checkout container by Docker ID, including services behind Compose profiles. They do not delegate to Devenv's profile-filtered start/stop commands. Partially running stacks expose both submenu actions, and full Docker container names remain visible beneath service names. Setup still delegates to `worktree-up.sh`; its repeat action explicitly names the shared Redis flush, and environment details explain the cross-checkout cache effect.

Deployment preflight separates branch search from the committed deployment draft. A keyboard-accessible branch picker keeps suggestions out of the form after selection; workflows use the selected branch's contracts, preserve workflow-specific options, and expose non-default options outside the disclosure. Reset uses a read-only summary. The renderer owns cancellation, latest-response handling, expiry and explicit retry; ambiguous submission transport failures direct the user to system activity rather than replaying a dispatch. Branch suggestions use a bounded thirty-second query cache and workflow contracts a bounded five-minute ref-keyed cache, with shared in-flight reads. Lookup and preparation do not repeat the full GitHub readiness probe; exact branch validation uses GitHub's exact ref endpoint, and reset uses one preparation path. Optional preparation request IDs use the existing desktop read-cancellation RPC. Dispatch retains fresh readiness/Argo checks, single-use plans and system locks. No local checkout is assumed and no Git fetch runs from preflight.

Preflight stories mount the production dialog through the Boc-owned `@boc/extensions/deployments/preview` entry point. Browser coverage in `packages/boc/component-tests/deployments.spec.ts` exercises keyboard selection, option preservation, delayed preparation, retry, expiry, reset summaries and narrow RTL layout; controller and service tests cover stale responses, cancellation, workflow-specific drafts and remote command counts.

## Upstream integration surface

Worktree avatar rings use a neutral two-pixel separator and a two-pixel semantic status ring: dashed accent for worktrees without a configured stack or unknown status, solid success/warning for running/partial stacks, and dashed muted for stopped stacks. Visible local worktree tabs share checkout-scoped environment polling with the panel and expose status/count tooltips. Avatar slots reserve the ring's full bounds to avoid hover/selection-mask clipping in either text direction.

No upstream component is intentionally copied into Boc. When a conflict tempts a copy, first look for a bridge, registry, Effect `Layer`, plugin, RPC group, or channel branch.

The fork-added `server.boc.worktree` and `server.boc.environment` HTTP groups are retired without compatibility handlers. Boc clients use `api.rpc(BocEnvironmentRpc.Rpc)` from Schema's Boc namespace. Its registration identity is `boc.environments.v1`, with capability protocol 2 required by the desktop compatibility probe for container inventory/actions, log reads, and operation-terminal resize; it registers only on Boc backends, so ordinary upstream backends report a missing RPC. The former `boc.worktrees.v1` RPC is removed without a compatibility handler. Public client generation and its inventory assertion match the common upstream baseline.

Environment RPC registrations delegate to the existing global backend and persistent PTYs; plugin disposal does not own operation locks or cancel its processes. Environment calls bind the checkout Location explicitly, and environment records retain their disk/handoff behavior.

## Project Controls verification and limits

The former `@bergflow/opencode` artifact and its fallback bootstrap are removed. Native wire contracts live under Schema's Boc namespace. Policy migration copies the prior project policy into `boc:controls:<projectID>` without deleting legacy values; subsequent reads use Boc storage. Unsupported saved overrides remain visible and removable. Persistence precedes application to every active Location; application failures remain visible and retryable.

Desktop verifies the environment and native Controls RPC contracts at its probe Location during backend selection. A backend missing a contract goes through the existing handoff/replacement flow, including isolated backends with the same version. Boc stages bundled server binaries by compatibility version plus artifact digest so a new Boc build cannot reuse an older binary merely because the official version matches. The desktop `bun run dev:boc` source-backed workflow compiles the backend with the Boc channel and retains blue local branding, the local desktop identity and isolated database. Plain `bun run dev` is the upstream development entry point. Project Controls has no server-setup panel. The official compatibility pin is `2.0.3`, built from upstream tag `v2.0.3`. Existing externally configured Bergflow plugins are not edited or uninstalled by Boc and can still impose their own policies.

## Boc desktop build commands

Run these from `packages/desktop`:

- `bun run dev:boc`: source-backed local Boc development; accepts `--build-server` or `--download-server <version>` and forwards remaining Electron/Vite arguments. Download mode clears source/WSL build overrides. Source mode supplies the WSL CLI build/output paths.
- `bun run build:boc`: stages a fork-built CLI from `OPENCODE_CLI_DIST`, prepares red release icons, then invokes upstream Electron/Vite with `OPENCODE_CHANNEL=boc`. Set the Boc application `OPENCODE_VERSION`; `OPENCODE_CLI_TARGET` uses the upstream target inventory.
- `bun run prepare:boc`: performs the same staging and writes the requested application version into the desktop package manifest for release packaging.
- `bun run package:boc`: uses the Boc-owned Electron Builder overlay. The release workflow selects this same config explicitly for platform packages.

The overlay retains upstream dependency exclusions, macOS entitlements/signing/notarization, NSIS hooks and CLI `afterPack` validation. It replaces precomputed app/protocol/Linux identities, metainfo paths and updater metadata. Unsigned Windows builds use an explicit no-op app signing callback and skip CLI signing; signed builds retain upstream signing and place the publisher under Electron Builder's `win.signtoolOptions`.

Packaging coverage lives in `packages/boc/scripts/desktop/packaging.test.ts` and runs with the Boc suite. It verifies all upstream target mappings, platform identity/resource composition, signed/unsigned Windows policy, and development argument/environment selection. Actual signing, notarization and Windows/Linux installer execution remain release-runner checks.

Project agent and MCP activation uses native checkout configuration. Controls edits `.opencode/opencode.jsonc` in the selected Location, preserving JSONC comments and complete inherited MCP definitions. The global editor and Global-scope agent/MCP switches target the server's global `opencode.jsonc`; project-row switches never write global files. Existing MCP policies remain effective until individually migrated by a native mutation. Disabled native agents remain in inventory, while externally registered agents whose final transform ordering is not controlled remain read-only. Native changes follow OpenCode's normal reload behavior. Project tool/skill/instruction policy and the server-wide global hard-off policy guard future execution through existing hooks; the global policy applies only to globally sourced supported capabilities and is not understood by an unextended official server. Already running operations continue. Registered tool inventory is not a promise that every tool is available in every model request.

Configuration/source saves use content revisions and validate through native normalization and skill parsing. Source editing and removal resolve bounded inventory-owned skill/instruction files; creation uses native scoped skill directories or `AGENTS.md`. Legacy global skills under `~/.opencode` are included in the global source scope. Deletion removes only the source file. The UI explicitly distinguishes global source editing from project activation, hides the save confirmation during delete confirmation, and uses semantic success/danger status colors and a danger delete action. Files are not silently ignored or untracked in Git. The compact table shows aligned source/model/action columns, keeps descriptions in expandable row details, and uses shared Select, SegmentedControl, Dialog, Popover and List components. The model picker uses the connected server's native model catalog, including variants, through the fork-owned host bridge.

`packages/core/test/boc/controls.test.ts` exercises the native RPC with real registries, policy enforcement, source reporting, instruction selection, migration and revision conflicts. `packages/app/src/boc/controls.stories.tsx` mounts the production screen; `packages/boc/component-tests/controls.spec.ts` checks inline origins, keyboard search/toggles, focus, system-tool collapsing/search and narrow layout. Environment browser coverage also lives in `packages/boc/component-tests/`. Run both with `bun run test:components` from `packages/boc`; the owned config composes the shared Storybook runner and keeps reports under the Boc package. The old artifact lifecycle script is removed.

## Merge risk order

1. Inspect every incoming commit and changed file in `packages/core`, `packages/app`, and `packages/desktop`; commit scopes such as `fix(core):`, `fix(app):`, and `fix(desktop):` are priority signals, not the only filter.
2. Review `packages/protocol`, `packages/schema`, `packages/server`, `packages/client`, and `packages/ui` when they touch an API or seam listed above.
3. TUI-only changes are normally low priority. Raise them when they also change shared core, protocol, schema, client, UI, or server behavior.
4. A clean textual merge is not proof of compatibility. Check renamed APIs, changed defaults, new native extension points, provider order, generated clients, and build-time behavior.

## Required verification

Run checks from their package directories; never run tests from the repository root.

```text
packages/boc:     bun typecheck && bun run test
packages/app:     bun typecheck && bun test --conditions=solid --preload ./happydom.ts src/boc
packages/desktop: bun typecheck && bun test
repo root:        bun packages/boc/scripts/audit-fork-surface.ts
```

Also run `bun run generate` from `packages/client` after public Protocol or Server `HttpApi` changes. Build app/desktop when routing, channel identity, bundling, lazy loading, IPC, or packaged resources change. Run focused core/server/client checks when their APIs are involved.

## Renderer product identity

`packages/app/src/boc/product-vite.ts` runs after upstream's Vite configuration hook. Boc release renderers use `beta` behavior with `VITE_BOC_PRODUCT="boc"`; local development retains `local` behavior with `"boc-dev"`. Electron main and the backend retain their existing Boc-aware identities. Titlebar copy uses Boc's existing `boc.title` key; icons, notifications and empty-panel marks use the product input. Ordinary upstream modes have no Boc product input. Final configuration coverage runs both build/serve for Boc, local, dev, beta, prod and latest in fresh processes under `packages/desktop/src/boc/product.test.ts`.

Standalone Boc web builds compose the upstream app config: from `packages/app`, run `OPENCODE_CHANNEL=boc bunx vite build --config ../boc/scripts/web/vite.config.mjs` (use `local` for blue development branding). The owned branding plugin supplies desktop/web favicon assets and a Boc web manifest. It does not transform upstream source code.
