# Boc fork integration map

This is the operational map of Boc's deliberate differences from `upstream/beta`. It is not a changelog or roadmap. Read it before changing a fork integration or merging upstream.

## Maintenance contract

- Update this file in the same commit that adds, changes, replaces, or removes a fork capability, upstream seam, or upstream API dependency.
- Describe only implemented behavior. Plans and experiments become entries when their code lands.
- Keep product code in fork-owned paths. If an upstream-owned file must change, keep the change narrow and record it here and in `packages/boc/fork-surface.json`.
- Prefer a supported upstream extension point over a Boc workaround. Remove obsolete seams when upstream makes them unnecessary.
- Treat `packages/boc/fork-surface.json` as the exact machine-readable path list and this file as the explanation of intent and coupling.
- The surface audit compares the working tree against the common upstream baseline, includes untracked non-ignored files, and rejects duplicate, stale and unlisted approvals. It checks both sides of renames against the ownership rules.

Checkout-path copying is available in both menus; macOS desktop additionally opens that checkout in Terminal through the existing platform API. The checkout preparation panel adds elapsed time, source path, requested branch, named phases, connection feedback, and bounded live Rift/startup output correlated by the pending Session ID. It polls the Boc preparation read model while creation continues independently on the backend; terminal spinner and color controls are rendered as readable text rather than reproduced interactively.

Project Controls supplies producer metadata in its native state response: exact agent/MCP configuration files, skill/instruction paths, and registering plugin identity. Origins distinguish System, Global, Project, and Plugin (registered capabilities without a filesystem scope). MCP tools inherit their server's source when available. Icons remain immediately before names. Ctrl+F/Cmd+F focuses and selects the shared V2 TextInput, yielding to dialogs. The new route is `/boc/controls`; old `/boc/bergflow` links, the local selection preference key, and existing English i18n keys remain compatible.

The native `boc.project-controls` built-in activates only in the Boc channel, after configuration producers. Its RPC identity is `boc.controls.v1`. Project policy and mutation serialization are process-global services; inventory and scoped subscriptions belong to each Location. Desktop is the supported management UI. There is no CLI/TUI control screen or installation workflow.

The host plugin loader uses upstream registration precedence and source handling. The obsolete fork-added fallback registration option and public module-schema export are retired; external embedders using those additions must migrate to ordinary registration. Project Controls does not use either addition. Controls use authenticated plugin RPC through the existing app server client, without changing HTTP APIs or desktop service ownership. Ambient instruction selection is now an internal Location-scoped Controls service; the fork-added external Effect/Promise selection facade is retired. Controls receives structured candidates before filtering, including disabled sources, and permits only project-owned mutations. Nested read-triggered instructions and already admitted Session history are unaffected.

Session search uses the upstream implementation from `370b9965d3` without Boc overrides. The former Boc page-search implementation has been removed.

## Project Controls verification and limits

The former `@bergflow/opencode` artifact and its fallback bootstrap are removed. Native wire contracts live under Schema's Boc namespace. Policy migration copies the prior project policy into `boc:controls:<projectID>` without deleting legacy values; subsequent reads use Boc storage. Unsupported saved overrides remain visible and removable. Persistence precedes application to every active Location; application failures remain visible and retryable.

Desktop automatically verifies both Rift and the native Controls RPC during backend selection. A backend missing Controls goes through the existing handoff/replacement flow, including isolated backends with the same version. Boc stages bundled binaries by compatibility version plus artifact digest so a new Boc build cannot reuse an older binary merely because the official version matches. The normal desktop `bun run dev` source-backed workflow compiles the backend with the Boc channel, fetches the matching Rift artifact, and retains the local desktop identity and isolated database. Project Controls has no server-setup panel. The official compatibility pin remains `0.0.0-beta-19234`. Existing externally configured Bergflow plugins are not edited or uninstalled by Boc and can still impose their own policies.

Agents remain read-only because the public transform API has no final-selection phase. Tool and skill controls also guard future execution through existing hooks. Already running operations continue. Registered tool inventory is not a promise that every tool is available in every model request.

`packages/core/test/boc/controls.test.ts` exercises the native RPC with real registries, policy enforcement, source reporting, instruction selection, migration and revision conflicts. `packages/app/src/boc/controls.stories.tsx` mounts the production screen; `packages/boc/component-tests/controls.spec.ts` checks inline origins, keyboard search/toggles, focus and narrow layout. Environment browser coverage also lives in `packages/boc/component-tests/`. Run both with `bun run test:components` from `packages/boc`; the owned config composes the shared Storybook runner and keeps reports under the Boc package. The old artifact lifecycle script is removed.

| API or contract | Boc use | Watch for |
| --- | --- | --- |
| `@opencode-ai/core/worktree` (`Worktree.Strategy`, strategy IDs, optional progress observer, and registration/composition) | Implements and selects `boc/rift`, reports tracked creation phases, and streams observed startup output. | Strategy input/output changes, selection semantics, plugin registration, worktree persistence, setup command execution, removal safety. |

| Generated `@opencode-ai/client` Promise/Effect clients | App-side Rift capability, cleanup, and development-environment calls. | Operation identifiers, generated method names, request shape changes; regenerate from `packages/client` after public API changes. |
| App routing, command, language, platform, server, dialog, workspace, and tab hooks | Fork-owned bridges adapt Boc features to the app shell. | Context/provider placement, route parsing, command registration lifecycle, workspace creation/cache semantics, draft creation, and session tab selection. |
| Desktop `DesktopRpcs`, handler-owned storage services, renderer `invoke`, `DesktopPaths`, `CHANNEL`, and background-service startup | Connects Boc renderer/main code, stages Rift, probes Boc capability, and negotiates shared versus isolated service ownership. | IPC client typing, provider order, SQLite storage ownership, dependency externalization, service discovery/version semantics, PTY handoff, and lifecycle changes. |

Imports from `effect/unstable/*` and internal app/desktop modules are deliberate but high-coupling dependencies. Prefer stable public replacements when upstream introduces them.

## Merge risk order

1. Inspect every incoming commit and changed file in `packages/core`, `packages/app`, and `packages/desktop`; commit scopes such as `fix(core):`, `fix(app):`, and `fix(desktop):` are priority signals, not the only filter.
2. Review `packages/protocol`, `packages/schema`, `packages/server`, `packages/client`, and `packages/ui` when they touch an API or seam listed above.
3. TUI-only changes are normally low priority. Raise them when they also change shared core, protocol, schema, client, UI, or server behavior.
4. A clean textual merge is not proof of compatibility. Check renamed APIs, changed defaults, new native extension points, provider order, generated clients, and build-time behavior.

## Required verification

Run checks from their package directories; never run tests from the repository root.

```text
packages/boc:     bun typecheck && bun run test
packages/app:     bun typecheck && bun test --conditions=solid --preload ./happydom.ts src/boc
packages/desktop: bun typecheck && bun test
repo root:        bun packages/boc/scripts/audit-fork-surface.ts
```

Also run `bun run generate` from `packages/client` after public Protocol or Server `HttpApi` changes. Build app/desktop when routing, channel identity, bundling, lazy loading, IPC, or packaged resources change. Run focused core/server/client checks when their APIs are involved.
